1How data flows today

There are two independent pipelines into JustGains. The device path reads whatever landed on the phone's health store; the cloud path pulls provider accounts (currently Strava) through our self-hosted open-wearables instance. Both converge on the same FitnessActivities table and render identically in the feed.

3What's solid

Idempotent everywhere

Every layer dedups: OW has unique (data_source, start, end) + insert-or-return; JG has unique (creator, source, externalId) with batch upsert; mobile imports carry stable healthkit:UUID / strava:{id} external IDs. Re-syncs update in place — verified live.

Routes are first-class, end to end

One format (Google Encoded Polyline, precision 5) from all three sources. Renders in the mobile feed RouteMap, the debug screen, and now the OW dashboard — all dependency-free SVG. Verified with real Strava GPS data.

Security model is right

OW API key lives only server-side; mobile talks to JG which proxies. OAuth callback creates the connection server-side before redirecting, so browser dismissal can't lose a connection. Per-user OW mapping is server-managed JSONB.

Future providers are credentials-only

OW already normalizes Garmin, Polar, Oura, Whoop, Suunto, Fitbit + Apple/Samsung/Google SDK push + FIT files. JG now maps all of them (ActivitySource + sync service), and ConnectedApps loads its provider list from GET /user/wearables/providers. Adding a provider = configuring its OAuth credentials on the OW platform. Nothing else.

7Failure modes & graceful degradation Tested live June 11

The app must lose zero quality when the open-wearables platform is down or the device is offline — wearables sync is an enhancement layered onto a working app, never a dependency. Verified by pointing the API at a dead OW address and probing every endpoint.

FailureWhat happensRecovery
OW platform down — user opens Connected Apps Interactive calls fail fast (8 s cap; ~2 s when refused — measured) with clean 400 envelopes, never 500s or hangs. The provider list is served from the API's last-successful cache; if even that's cold, the app falls back to its built-in list. Connections show "pull to retry". Automatic on next request
OW down — app foreground / debug-screen sync Foreground sync is fire-and-forget with a swallow-all catch — completely invisible to the user. The debug screen shows its inline error message. Device health-store sync is independent and continues normally. Next foreground / tap
OW down — hourly background pass Per-user failures are logged and skipped; after 3 consecutive failures the pass aborts (circuit breaker) instead of burning a timeout per user. Next hourly pass
OW down — webhooks None arrive (OW emits them), so nothing to handle. In-flight deliveries are queued by Svix and retried with backoff. Svix retry / next pass
JustGains-API down — webhook delivery Receiver returns non-2xx → Svix retries with exponential backoff; the hourly pass and foreground syncs also re-cover the window (everything is idempotent upserts). Svix retry
Device offline Health-store reads are local and keep working; daily metrics persist to the local DB and queue for the next /sync. The activity-import cursor only advances when the import actually reached the server (bug found & fixed here — offline workouts previously fell out of the window permanently). Feed renders from SWR cache; wearables sync silently no-ops. Next online sync, no data loss
Strava down Upstream of OW — sync tasks fail inside OW and log; nothing user-visible in JustGains. OW's next poll / webhook

Measured with the API pointed at a dead OW URL: providers / connections / sync-all / connect / disconnect all returned structured 400s in ≈2 s; after restoring the URL, everything recovered instantly with the Strava connection intact.

8Future: syncing workouts out to Strava & friends Way later — design sketch

Everything above is inbound (provider → JustGains). The reverse — a strength session logged in JustGains showing up on the user's Strava profile — is a different feature with its own constraints. Nothing here is built; this is the plan for when it's wanted.

What already works today (the lazy path)

On workout completion, healthWrite.ts already writes the session into Apple Health / Health Connect. Users who enable Strava's own "import from Apple Health"-style integrations get JG workouts on Strava with zero work from us. Worth documenting for users before building anything.

How a real push would work

PieceDetail
Strava API POST /api/v3/activities creates a manual activity (name, sport type, start, elapsed time, description, optional distance) — right fit for gym sessions, which have no GPS file. GPS workouts would use POST /api/v3/uploads with a generated TCX/GPX instead.
OAuth scope Pushing requires activity:write. Current connections are read-only (activity:read_all,profile:read_all), so users must re-authorize — gate this behind a "Share workouts to Strava" toggle that triggers a fresh connect flow with the wider scope.
Where the code lives Provider tokens deliberately live only in open-wearables — JustGains never sees them. So the push belongs in OW as a small generic endpoint (POST /api/v1/users/{id}/providers/{provider}/workouts) that maps a normalized workout onto each provider's create-activity API. JG calls it server-side after workout completion. This is also the most valuable upstream PR of the bunch — OW currently has no outbound push at all.
Echo prevention A pushed workout comes straight back via the Strava→OW webhook. Two guards: stamp the Strava activity's external_id with a JG marker (e.g. justgains:{workoutLogId}) and skip those on import; the cross-source dedup pass (G2) is the backstop if a marker is ever lost.
UX Per-provider toggle in Connected Apps ("Share completed workouts to Strava"); fire-and-forget push on workout completion with a retry queue; respect deletes (user deletes the JG workout → delete the pushed Strava activity via its stored id).
Other providers Garmin/Polar/etc. have far more restrictive (or no) write APIs — Strava is realistically the only push target. Design the OW endpoint generically but ship Strava-only.

Rough order when picked up: ① OW push endpoint + Strava manual-activity mapper, ② activity:write re-auth flow + toggle, ③ echo-prevention marker on import, ④ push-on-completion + delete propagation. Roughly 2–3 days end to end, dominated by the re-auth UX and echo testing.
