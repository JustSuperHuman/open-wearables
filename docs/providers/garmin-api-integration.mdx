## Overview

Garmin Connect provides access to comprehensive fitness and health data from Garmin devices through their Wellness API. The integration supports activities, daily summaries, sleep data, body composition, and more.
Through the Garmin Connect platform, you can access data from:

- Health API
- Activity API
- Women’s Health API
- Training API
- Courses API

Once you get access to the Developer Portal, you’ll find the full docs, including the [FAQ page](https://developerportal.garmin.com/developer-programs/faqs) and [specification documents](https://developerportal.garmin.com/developer-programs/programs-docs).

## Access tiers

Garmin has reopened the [Garmin Connect Developer Program](https://developer.garmin.com/gc-developer-program/overview/) with two business tiers:

| | Starter | Enterprise |
|---|---|---|
| Who it's for | Organizations getting started | Companies operating at scale |
| Data delivery | Push only | Push or Ping/Pull |
| Historical data | Not included | 1 month+ |
| User capacity | Up to 1,000 connected users | Unlimited |
| Technical support | - | Included |
| How to get it | Create an app with Starter access after joining the program | Request through the Garmin Developer Portal, commercial terms agreed with Garmin |

Open Wearables works with push delivery, so both tiers are supported. Starter doesn't include historical data, so the backfill described below is only available on Enterprise; on a Starter app, set `GARMIN_BACKFILL_ENABLED=false` (see [Starter tier: no historical data](#starter-tier-no-historical-data)). You can move from Starter to Enterprise later.

Garmin describes both business tiers as intended for organizations (company, university, hospital, research institution, etc.). Individuals who only need their own data should look at the Personal API below.

<Note>
**Personal API**: Garmin also launched a [Personal API](https://developer.garmin.com/gc-developer-program/personal/personal-api/) that lets individual users access their own Garmin Connect data with a personal API key. It has a different base URL, authentication and endpoints than the business APIs, so **it doesn't work with Open Wearables yet**. We may add support for it in the future.
</Note>

<Steps>
  <Step title="Apply for Garmin developer access">
    Garmin access is approval-based. To apply, submit the official form:

    - [Garmin Connect Developer Program Access Request Form](https://www.garmin.com/en-US/forms/StarterGarminConnectDeveloperAccess/)

    After approval, you create an app with Starter access. Enterprise access can be requested through the Garmin Developer Portal.

    <Note>
    **Tips to avoid rejection:**
    - Apply **as a company/institution**, not as an individual.
    - Use a **company-domain email**.
    - Clearly explain the enterprise/commercial product or institutional use case.
    - Provide a public link to your app/website privacy policy.
    </Note>

    <Note>
    Make sure your mail server allows messages from:
    - `garmin.com`
    - `health.garmin.com`
    - `developer.garmin.com`
    </Note>
  </Step>

  <Step title="Get access to Garmin Developer Portal and add your team">
    After approval, Garmin will invite you to the Developer Portal and share a “set password” link.

    <Note>
    **Common Garmin restrictions**:
    - No generic inboxes (`support@`, `info@`, `dev@`, etc.)
    - No free mail (`gmail`, `outlook`, etc.)
    - Third-party integrators may require an NDA (handled with Garmin via ticket/email)
    </Note>
  </Step>

  <Step title="Create an Evaluation app (this gives you Client ID + Client Secret)">
    You must create an app in the Developer Portal first. Start with an evaluation app:

    - Go to your team apps page (example): `https://developerportal.garmin.com/teams/{your_team_name}/apps`
    - Create an app and set the type to **Connect Developer - Evaluation**
    - Set the **OAuth redirect URL** (where the user is sent after Garmin login in the 3-legged OAuth flow). Open Wearables derives this from your `API_BASE_URL` as `{API_BASE_URL}/api/v1/oauth/garmin/callback`, so register that exact URL here
    - Provide legal company details and describe how you will use Garmin data (aggregated/anonymous vs linked to identifiable users)
    - Select the APIs you intend to use (Health / Activity / Women’s Health / Training / Courses)

    <Note>
    One company account can manage multiple apps (e.g., if you run separate apps for different clients).
    </Note>

    This generates:
    - **Client ID**
    - **Client Secret**

    <Warning>
    Treat the Client Secret like a password. Store it in your secrets manager (and rotate if compromised).
    </Warning>
  </Step>

  <Step title="Configure API Tools (endpoints + data types/scopes)">
    Garmin’s API Tools are configured per app. To access them, log in with that app’s **Client ID** + **Client Secret**.

    **Enable endpoints**
    - Open [API Endpoints](https://apis.garmin.com/tools/endpoints)
    - For **every** endpoint, set the URL to your Open Wearables webhook push endpoint:

    ```
    https://<your-domain>/api/v1/garmin/webhooks/push
    ```

    For local development with ngrok:
    ```
    https://<your-ngrok-id>.ngrok-free.app/api/v1/garmin/webhooks/push
    ```

    In production, add a shared secret to the URL so only Garmin can post to it. See [Securing the push URL](#securing-the-push-url).

    - Set delivery type to **push** (dropdown on the right)
    - Check **enabled** for each endpoint you want to activate
    - All endpoints use the **same URL** — Garmin distinguishes data types internally and sends the appropriate payload to this single endpoint

    **Which endpoints to enable:**

    Enable **all** endpoints listed on the page. Open Wearables accepts data from all Garmin data types (activities, dailies, sleeps, epochs, HRV, body compositions, stress, respiration, pulse ox, and more).

    A subset of these types is actively requested during historical backfill — which ones is determined by `BACKFILL_DATA_TYPES` in `backend/app/services/providers/garmin/backfill_config.py`. All other enabled endpoints will passively receive data whenever Garmin pushes new updates.

    <Warning>
    **Backfill requirement**: backfill only works once the relevant endpoints are enabled on this page.

    Once backfill is enabled and data is ready, Garmin will deliver notifications via push and Open Wearables can ingest the backfilled data.
    </Warning>

    <Note>
    **Backfill limits (practical gotchas):**
    - Backfill needs historical data access, which is only included in the Enterprise tier.
    - Backfill typically returns **~last month** of data.
    - Each data type can usually be **backfilled only once**.
    - Don’t retry backfill over and over—if you need more history, check the Garmin docs for the supported process and limits.
    - You can query just one day in the same time at maximum — you can’t fetch an entire month in a single request.
    - In the user authorization (consent) screen, the **backfill scope is always turned off by default**, so users must manually enable it each time.
    </Note>

    **(Optional) Modify data types and OAuth scopes**
    - If you need to adjust what your app can access, open [API Configuration](https://apis.garmin.com/tools/apiConfiguration)
    - Pick which **data domains** your app is allowed to access
    - Pick which **OAuth scopes** will be shown/required during user authorization

    <Note>
    Keep scopes minimal: only request what Open Wearables actually needs for your use case. If you add new data domains later, you’ll typically need to update this configuration and re-verify.
    </Note>
  </Step>

  <Step title="Provide Garmin credentials to Open Wearables">
    Once you have an app created, configure your Open Wearables backend with:

```bash

GARMIN_WRITE_TIMEOUT_SECONDS=20           # total time budget of one workout/schedule/course request
GARMIN_WRITE_CALL_TIMEOUT_SECONDS=10      # longest wait for a single Garmin call
GARMIN_WRITE_CONCURRENCY=8                # Garmin write requests running at once
```

    <Note>
    If you later move from evaluation to production, you’ll update these credentials to the production ones.
    </Note>
  </Step> 
  <Step title="Go to production (partner verification + production access)">
    Evaluation apps are for internal development. To go production, Garmin requires partner verification:

    - Open [Partner Verification](https://apis.garmin.com/tools/partnerVerification)
    - Complete the checks/tests listed there
    - After you pass, apply for a **production key / production access**

    <Warning>

    </Warning>
  </Step>

## Starter tier: no historical data

Starter apps get push data from the moment a user connects, and nothing older. Garmin's backfill API is Enterprise-only, so on a Starter app every backfill request would fail. Set:

```bash
GARMIN_BACKFILL_ENABLED=false
```

With the flag off:

- Connecting a user through OAuth doesn't start a backfill, even with `HISTORICAL_SYNC_ON_CONNECT=true`. The connection is `active` straight away and no historical sync run is created for it.
- `POST /api/v1/providers/garmin/users/{user_id}/sync/historical` answers `400` with a message naming the flag.
- `GET /api/v1/users/{user_id}/connections` reports `webhook_callback: false` for Garmin, so clients can hide "sync history" options.
- Live pushes never chain into backfill requests, and any backfill task still queued from before the switch stops without calling Garmin.

The flag defaults to `true`, which keeps the Enterprise behaviour described above.

## Securing the push URL

Garmin doesn't sign its pushes. It identifies itself with a `garmin-client-id` header, and Open Wearables rejects any push whose header doesn't match `GARMIN_CLIENT_ID`. Your client id isn't a secret, though: it's in every OAuth link your users open. To make sure a push really comes from Garmin, put a shared token in the URLs you register in Garmin's portal.

Garmin's API Tools page drops the query string when it saves an endpoint URL, so the token goes in the path, as the last segment after `/t/`:

```
https://<your-domain>/api/v1/providers/garmin/webhooks/t/<GARMIN_WEBHOOK_TOKEN>
```

| Setting | Default | Effect |
|---|---|---|
| `GARMIN_WEBHOOK_TOKEN` | unset | The token expected in the URL, compared in constant time. Store it as a secret. |
| `GARMIN_WEBHOOK_TOKEN_REQUIRED` | `false` | `true`: a push without the right token gets `401`, on top of the client id check. `false`: the push is accepted and a warning is logged (without the token). |

The token is read from the path (`/webhooks/t/<token>`) or, for callers that keep query strings, from `?token=`; either one matching counts. The deprecated routes take it the same way: `/api/v1/garmin/webhooks/push/t/<token>` and `/api/v1/garmin/webhooks/ping/t/<token>`. Open Wearables refuses to start with `GARMIN_WEBHOOK_TOKEN_REQUIRED=true` and no token, since that would reject every push. The access log, webhook logs and Sentry events show the path token as `REDACTED` (`[Filtered]` in Sentry) and mask `?token=` values.

Roll it out in this order so no push is rejected while Garmin still uses the old URLs:

<Steps>
  <Step title="Set the token, not yet required">
    ```bash
    GARMIN_WEBHOOK_TOKEN=$(openssl rand -hex 32)
    GARMIN_WEBHOOK_TOKEN_REQUIRED=false
    ```
    Deploy. Pushes keep working with or without the token.
  </Step>
  <Step title="Update every endpoint URL in Garmin's portal">
    In [API Endpoints](https://apis.garmin.com/tools/endpoints), change each enabled endpoint to:
    ```
    https://<your-domain>/api/v1/providers/garmin/webhooks/t/<GARMIN_WEBHOOK_TOKEN>
    ```
    Use a token of hex characters (as `openssl rand -hex 32` gives you) so it needs no URL encoding. After saving, reopen the page and check that the stored URL still ends in `/t/<token>`.
  </Step>
  <Step title="Confirm Garmin sends the token">
    Wait for a few pushes, then check the API logs: `Accepted Garmin push without a valid URL token` (action `webhook_token_not_enforced`) should no longer appear.
  </Step>
  <Step title="Enforce it">
    Set `GARMIN_WEBHOOK_TOKEN_REQUIRED=true` and redeploy.
  </Step>
</Steps>

To rotate the token, repeat the steps with `GARMIN_WEBHOOK_TOKEN_REQUIRED=false` while you change the URLs.

## Keeping Garmin connections alive

A Garmin access token lasts 24 hours, and its refresh token expires 90 days after it's issued. Every refresh issues a new pair. Pushes don't need a token, so a user who never writes to Garmin could leave theirs untouched long enough to die. An hourly job (`refresh-garmin-tokens-hourly` in Celery beat) refreshes any token older than `GARMIN_REFRESH_TOKEN_MAX_AGE_DAYS` (60). Running it more often, or twice at once, is harmless. The same job fills in the Garmin user id of any connection that was saved without one because Garmin didn't answer at connect time; a lookup is also queued right after such a connect.

When Garmin rejects a refresh token, or rejects a freshly refreshed access token, the connection's status becomes `expired` and a `connection.revoked` webhook goes out with `reason` `refresh_failed` or `unauthorized`. An expired Garmin connection still receives and stores everything Garmin pushes, because only a deregistration ends the user's consent. Writes answer `garmin_not_connected` until the user reconnects Garmin, which sets the connection back to `active`. A deregistration push revokes both active and expired connections.

## Pushing workouts, schedules and courses

If your app has the Training API and Courses API enabled, Open Wearables can write to a user's Garmin Connect account for you. Your backend never handles Garmin tokens: it calls these endpoints with your Open Wearables API key, and Open Wearables makes the Garmin call with the stored connection, refreshing the token when needed.

| Method | Path | Needs permission | Success |
|---|---|---|---|
| `GET` | `/api/v1/users/{user_id}/garmin/permissions` | - | `200` |
| `POST` | `/api/v1/users/{user_id}/garmin/workouts` | `WORKOUT_IMPORT` | `201` |
| `PUT` | `/api/v1/users/{user_id}/garmin/workouts/{workout_id}` | `WORKOUT_IMPORT` | `200` |
| `DELETE` | `/api/v1/users/{user_id}/garmin/workouts/{workout_id}` | `WORKOUT_IMPORT` | `204` |
| `POST` | `/api/v1/users/{user_id}/garmin/schedules` | `WORKOUT_IMPORT` | `201` |
| `DELETE` | `/api/v1/users/{user_id}/garmin/schedules/{schedule_id}` | `WORKOUT_IMPORT` | `204` |
| `POST` | `/api/v1/users/{user_id}/garmin/courses` | `COURSE_IMPORT` | `201` |
| `DELETE` | `/api/v1/users/{user_id}/garmin/courses/{course_id}` | `COURSE_IMPORT` | `204` |

Users choose permissions on Garmin's consent screen and can change them later in Garmin Connect, so check `/garmin/permissions` before offering "Send to Garmin". It reads the permissions live from Garmin and stores them on the connection. When Garmin can't be reached (a network error or a Garmin 5xx), it answers with the stored ones instead, which Garmin's `userPermissionsChange` push keeps current. A Garmin rate limit is answered as `garmin_rate_limited`, not hidden behind stored values.

```bash
curl https://api.example.com/api/v1/users/4f6c9c2e-8a51-4c47-9d1e-2b7f0c3a9e11/garmin/permissions \
  -H "X-Open-Wearables-API-Key: $OW_API_KEY"
```

```json
{
  "connected": true,
  "status": "active",
  "garmin_user_id": "7c2e91f04ab35d6e8f10c4a9b2d7e3f5",
  "permissions": ["ACTIVITY_EXPORT", "COURSE_IMPORT", "HEALTH_EXPORT", "MCT_EXPORT", "WORKOUT_IMPORT"]
}
```

A user who never connected Garmin gets `{"connected": false, "status": null, "garmin_user_id": null, "permissions": []}`. `"connected": false` with `"status": "expired"` means Garmin stopped accepting the user's authorization (see [Keeping Garmin connections alive](#keeping-garmin-connections-alive)): their data keeps arriving, but ask them to reconnect Garmin before sending anything. An empty `permissions` list on a connected user means they switched every permission off.

Permission changes pushed by Garmin carry the time of the change, and an older change arriving late never overwrites a newer one. They apply to every Open Wearables user linked to the same Garmin account.

### Workouts

The body is a Garmin Training API V2 workout object, sent to Garmin as you wrote it. Open Wearables fills in `workoutProvider` and `workoutSourceId` (the source name Garmin Connect shows the user) from `GARMIN_WORKOUT_PROVIDER` when you leave them out.

```bash
curl -X POST https://api.example.com/api/v1/users/4f6c9c2e-8a51-4c47-9d1e-2b7f0c3a9e11/garmin/workouts \
  -H "X-Open-Wearables-API-Key: $OW_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "workoutName": "Tempo Tuesday",
    "description": "15 min easy, 4 x 5 min at tempo, 10 min easy",
    "sport": "RUNNING",
    "segments": [{
      "segmentOrder": 1,
      "sport": "RUNNING",
      "steps": [
        {"type": "WorkoutStep", "stepOrder": 1, "intensity": "WARMUP", "durationType": "TIME", "durationValue": 900, "targetType": "OPEN"},
        {"type": "WorkoutRepeatStep", "stepOrder": 2, "repeatType": "REPEAT_UNTIL_STEPS_CMPLT", "repeatValue": 4, "steps": [
          {"type": "WorkoutStep", "stepOrder": 3, "intensity": "INTERVAL", "durationType": "TIME", "durationValue": 300,
           "targetType": "PACE", "targetValueLow": 3.58, "targetValueHigh": 3.83},
          {"type": "WorkoutStep", "stepOrder": 4, "intensity": "RECOVERY", "durationType": "TIME", "durationValue": 90, "targetType": "OPEN"}
        ]},
        {"type": "WorkoutStep", "stepOrder": 5, "intensity": "COOLDOWN", "durationType": "TIME", "durationValue": 600, "targetType": "OPEN"}
      ]
    }]
  }'
```

```json
{
  "workout_id": 98765432,
  "workout": {
    "workoutId": 98765432,
    "ownerId": 41925377,
    "workoutName": "Tempo Tuesday",
    "sport": "RUNNING",
    "workoutProvider": "YourApp",
    "workoutSourceId": "YourApp",
    "segments": ["..."]
  }
}
```

`workout` is whatever Garmin returned. Keep `workout_id` to update, schedule or delete the workout later, and keep `ownerId` too: Garmin requires it on updates. An update replaces the whole workout. If its body leaves out `ownerId` or `workoutProvider`, Open Wearables reads the current workout from Garmin first (one extra Garmin call) and keeps its `ownerId`, `workoutProvider` and `workoutSourceId`; `GARMIN_WORKOUT_PROVIDER` only fills a provider the workout never had. An update answers `200` with the same `{"workout_id", "workout"}` shape, and `garmin_not_found` when Garmin has no such workout.

In the rare case Garmin creates a workout without returning its id, the create still answers `201`, with `"workout_id": null` and whatever Garmin sent. Don't retry it: the workout exists in Garmin Connect. Schedules and courses behave the same way.

Before calling Garmin, Open Wearables checks that `sport` is set and that the workout stays within Garmin's limits: a single-sport workout has one segment and at most 100 steps; `MULTI_SPORT` allows 25 segments and 250 steps. A repeat block counts as a step, and so does every step inside it. `workoutProvider` and `workoutSourceId` may be at most 20 characters. Everything else (step types, exercise categories and names, targets) is validated by Garmin; its message comes back in a `garmin_validation_error`. Garmin expects speed targets, pace included, in meters per second, so convert from min/mi before sending.

```bash
  -H "Content-Type: application/json" \

```

```json

```

### Courses

The body is a Garmin Courses API course object. Open Wearables checks for a non-empty `courseName`, between 1 and 10,000 entries in `geoPoints` (Garmin's limit; it suggests a point every 100 m at most), and numbers (not `null`, strings or booleans) for `distance`, `elevationGain` and `elevationLoss`, in meters.

```bash
curl -X POST https://api.example.com/api/v1/users/4f6c9c2e-8a51-4c47-9d1e-2b7f0c3a9e11/garmin/courses \
  -H "X-Open-Wearables-API-Key: $OW_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "courseName": "Riverside loop",
    "description": "Flat 5 mi loop along the river path",
    "distance": 8046.7,
    "elevationGain": 31.0,
    "elevationLoss": 31.0,
    "activityType": "RUNNING",
    "coordinateSystem": "WGS84",
    "geoPoints": [
      {"latitude": 38.8977, "longitude": -77.0365, "elevation": 17.0},
      {"latitude": 38.8985, "longitude": -77.0352, "elevation": 18.5}
    ]
  }'
```

```json
{"course_id": 41887203, "course": {"courseId": 41887203, "courseName": "Riverside loop", "...": "..."}}
```

Deleting a workout, schedule or course answers `204`. One Garmin no longer has also answers `204`, so a retried delete is safe.

### Retries and `Idempotency-Key`

Each request gets `GARMIN_WRITE_TIMEOUT_SECONDS` (20 s) for all the Garmin calls it makes, and no single call waits longer than `GARMIN_WRITE_CALL_TIMEOUT_SECONDS` (10 s). When a create times out, your client can't know whether Garmin made the object. Send an `Idempotency-Key` header with every create (`POST` workouts, schedules and courses), a fresh value such as a UUID per object, and reuse it when you retry:

```bash
curl -X POST https://api.example.com/api/v1/users/4f6c9c2e-8a51-4c47-9d1e-2b7f0c3a9e11/garmin/schedules \
  -H "X-Open-Wearables-API-Key: $OW_API_KEY" \
  -H "Idempotency-Key: 6f1c2d8e-3b0a-4c55-9d2e-7a8b1c0f4e21" \
  -H "Content-Type: application/json" \
  -d '{"workout_id": 98765432, "date": "2026-11-03"}'
```

A retry with the same key within 24 hours gets the first response back (`201`, with an `Idempotent-Replayed: true` header) and nothing is created twice. Only successes are remembered: after an error, the same key runs the request again. Reusing a key with a different body, or while the first request is still running, answers `409 idempotency_conflict`. Keys are scoped to your API key, the user and the endpoint, and can be up to 255 characters.

Garmin writes run on their own pool of `GARMIN_WRITE_CONCURRENCY` (8) workers, separate from the one that receives Garmin's pushes, so a slow Garmin can't hold up data ingestion. A request that can't get a worker within 5 seconds answers `503 garmin_busy` with `Retry-After`.

### Errors

Every failure on these endpoints, authentication and request validation included, has the same shape:

```json
{"detail": "The user hasn't granted WORKOUT_IMPORT to this app in Garmin Connect.", "code": "garmin_permission_missing"}
```

| Status | `code` | When |
|---|---|---|
| `401` | `unauthorized` | The Open Wearables API key is missing or invalid. |
| `404` | `garmin_not_connected` | No active Garmin connection, or Garmin no longer accepts the user's authorization (the connection is now `expired`). Ask the user to reconnect. |
| `404` | `garmin_not_found` | Garmin has no such workout, schedule or course for this user (update, or the `ownerId` lookup). Deletes of a missing object still answer `204`. |
| `403` | `garmin_permission_missing` | The user hasn't granted the permission the call needs. A stored "not granted" is double-checked with Garmin before refusing. |
| `403` | `garmin_forbidden` | Garmin refused the call itself (its HTTP 403, "Not allowed"). Garmin's message is in `detail`. |
| `409` | `idempotency_conflict` | The `Idempotency-Key` was used for a different body, or its first request is still running. |
| `422` | `garmin_validation_error` | The request failed Open Wearables' checks, or Garmin rejected it. Garmin's own message is in `detail`. |
| `429` | `garmin_rate_limited` | Garmin's per-app or per-user rate limit was hit, including during a permission check. `Retry-After` is passed on when Garmin sends it. Open Wearables doesn't retry for you. |
| `502` | `garmin_upstream_error` | Garmin failed, timed out, or answered something unexpected. Retry later, with the same `Idempotency-Key` for a create. |
| `503` | `garmin_busy` | Too many Garmin writes in flight on this server. Retry after `Retry-After` seconds. |

When Garmin answers `401` to a token Open Wearables still considers valid, the token is refreshed once and the call retried. A second `401` marks the connection `expired` and answers `garmin_not_connected`.

Garmin rate-limits Training and Courses API calls per app and per user, with tighter limits on Starter apps. The limits for your tier are in Garmin's Training API and Courses API specifications. Each `/garmin/permissions` call and each update without `ownerId` or `workoutProvider` costs a Garmin call too, so cache permissions instead of checking before every write.

## What Open Wearables stores from Garmin pushes

Enable every endpoint in API Tools; anything Open Wearables doesn't store is acknowledged and dropped, so Garmin never retries it.

- **Activities and activity details** become workouts, with distance, calories, steps, average and max heart rate, average cadence (run, bike, swim or push), average and max speed, and total elevation gain. Times are stored in UTC.
- **Edits.** An activity the user edits in Garmin Connect arrives as `manuallyUpdatedActivities`, and the stored workout is updated in place: type, start, duration, distance, calories, heart rate and name. Fields the edit doesn't carry, such as laps from the FIT file, are kept, and a `workout.updated` webhook goes out with the workout's new values under the id `workout.created` announced. A copy of the original summary arriving after the edit (Garmin redelivers, or a retried task) doesn't undo it. If the edit moves the activity onto exactly the time span of another workout from the same device, the edit isn't applied and the push result reports a `conflict`.
- **Redeliveries.** Workouts are matched on the Garmin activity id first, so an activity Garmin sends twice stays one workout. A redelivery with different values updates it (and sends `workout.updated`); an identical one changes nothing and sends no webhook. `workout.created` goes out once, when the workout is first stored.
- **Nutrition** becomes daily totals of `dietary_energy_consumed`, `dietary_carbohydrates`, `dietary_fat_total` and `dietary_protein`. Individual foods aren't stored as meals because Garmin sends them without a timezone or an id. Each summary is the whole day, so a macro it leaves out is stored as 0 for that day: after the user deletes the only food with fat in it, the day's fat total drops to 0 instead of keeping the old number.
- **Hydration** becomes a daily `hydration` total in mL.
- **Breathing variations** aren't stored: no series type fits a breathing-variation level. With `RAW_PAYLOAD_STORAGE` enabled the raw push is kept like every other Garmin push.

### Device attribution

Garmin's brand guidelines ask for a "Garmin [device model]" attribution next to Garmin data. Workouts carry the model in `source.device`, taken from the `deviceName` Garmin sends with each activity. Per-second workout samples (with `INGEST_WORKOUT_SAMPLES=true`) are filed under the same device. Garmin doesn't always spell a device the same way (activity details and FIT files can differ in case, e.g. "Garmin fenix 8" and "Garmin Fenix 8"), so the first spelling stored for a user is kept and later ones that differ only in case are filed under it. Daily summaries, sleep, HRV, stress, nutrition and the other Health API data come without a device name, so their `source.device` is `null`; show plain "Garmin" for those, as the guidelines ask. Activities typed into Garmin Connect report their device as `unknown`, which Open Wearables stores as `null` too.
